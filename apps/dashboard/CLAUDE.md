# apps/dashboard

Guidance moved out of the root `CLAUDE.md` so it loads only when working in this app.

Naming rules are in the repo root's `NAMING.md`, and `lib/naming.test.ts` enforces the ones that can be. The two that bite most often here: an agent seam in a `*Deps` interface takes the exact factory name `@workspace/agents` exports (R2), and `components/` mirrors the route tree while `lib/` names domain concepts (R8).

## The auth gate

**The gate is two layers, and neither is sufficient alone.** `apps/dashboard/proxy.ts` — `proxy.ts`, not `middleware.ts`; Next 16 renamed the convention — matches everything except static assets, so a route added later is closed by default. The authoritative check is separate: pages call `getCurrentUser()` themselves, and `lib/chat-handler.ts` returns its own 401 before it parses a body. That duplication is deliberate. The proxy is a routing concern, and the chat route spends the OpenAI budget, so it must not be reachable because a matcher pattern was wrong.

**`app/(app)/layout.tsx` also calls `getCurrentUser()`, and that call is for the sidebar — not for the gate.** A layout does not re-render on navigation, so its check is not re-run when someone moves between routes; Next's own authentication guide warns about exactly this and prescribes the split used here — fetch the user in the layout to display it, keep the authorization check in each page. **Every page under the group therefore calls `requirePageUser()` (`lib/auth/require-page-user.ts`) itself, and deleting that call because "the layout already checks" reopens the hole.** The helper is only the three redirect lines that every page had copied verbatim; it is not a shared check performed once — each page still runs it, on every render. A new page under `app/(app)/` that does not call it is ungated no matter what the layout does. The duplicate call costs nothing: `getCurrentUser` is wrapped in React's `cache()`, so the layout and the page share one session lookup and one identity upsert per request. `cache()` and not a module-level memo — the scope has to be one request, or one person's identity is served to the next.

**For a Server Action the proxy is not a second layer at all — it is barely a first one.** `auth.middleware()` in `@neondatabase/auth@0.4.2-beta` cannot evaluate a non-GET request (its session fast path is guarded by `method === "GET"`), so `proxy.ts` degrades every POST to checking that _some_ session-cookie substring is present. A forged cookie gets past it. The check inside the action is therefore the only real one, which is why `lib/documents/document-actions.ts` calls `getUser()` before it touches the body. Next's own docs say the same thing independently: a Server Function is reachable by direct POST, not only through the UI.

**Server Actions follow a fixed shape, set by `app/(app)/documents/actions.ts`.** `"use server"` at the top of a dedicated `app/<segment>/actions.ts`, never inline — the set of exported actions is a security surface and belongs in one auditable place. That file is a thin wrapper; the logic lives in a `createXActions(deps)` factory under `lib/`, matching `lib/chat-handler.ts`, because the injectable seam is what lets the authorization branches be tested without a live session. **Nothing under `lib/documents/`, `lib/jobs/`, `lib/briefing-runs/`, `lib/postings/`, `lib/cover-letters/`, `lib/tailored-resumes/` or `lib/whiteboard/` imports Next**, which is what makes `pnpm turbo test --filter=@workspace/dashboard` able to cover them at all. Actions take `(state, formData)`, return a serializable discriminated union, and never throw for an expected failure. Cache invalidation is `refresh()` from `next/cache` — Server-Action-only in Next 16 — and stays in the wrapper, because it needs a request store.

Three things here are easy to undo by accident:

- **The proxy converts its redirect to a 401 under `/api/`.** The SDK only knows how to redirect to a login page, which for an API route means a `fetch` caller receives an HTML page with a success status and cannot tell it was refused. Removing that conversion also stops the chat route's own 401 from ever running, because the request no longer reaches it.
- **The SDK's skip list is hardcoded** — `/api/auth`, `/auth/callback`, `/auth/sign-in`, `/auth/sign-up` are ungated no matter what `config.matcher` says, and nothing in this repo can extend or override it. It is also why `/auth/sign-up` would be public if anyone built it.
- **`users.id` is the platform identity; the Neon Auth id is only a mapping.** `lib/auth/current-user.ts` returns the uuid from `users`, never `session.user.id`. That uuid is what `jobs.user_id` references and what becomes the `userId` segment of every S3 key, where `assertSegment()` in `@workspace/user-storage` treats it as the ownership boundary. `ensureUserForAuth(prisma, authUserId)` from `@workspace/db` — a free function, not a store method — is idempotent and race-safe, so it is safe on every request and self-heals; there is no transaction to coordinate with, because Neon has already created the account by the time our code runs. It reads first and creates only on a miss, so the common request is an index-only read rather than the `INSERT … ON CONFLICT` it used to be — a write transaction in front of every page.

**`callbackURL` is resolved on the server, and on a preview it is deliberately not the origin you are looking at.** The auth server checks `callbackURL` against Neon Auth's trusted domains _before_ it checks the provider, and an origin that is not on the list is refused with `403 INVALID_CALLBACKURL` — so `window.location.origin` made sign-in impossible on every preview deployment, because Vercel mints a new `control-panel-<hash>-….vercel.app` host per build and links that host from the PR comment. `lib/auth/callback-origin.ts` returns the stable `VERCEL_BRANCH_URL` alias instead, so one `neon neon-auth domain add` per branch covers every build on it. **`.github/workflows/preview-auth-domain.yml` is what runs that command** — on `pull_request` it reads the alias Vercel assigned (`meta.branchAlias`, never constructed: Vercel truncates a long branch to 13 characters plus six undocumented hex digits) and adds it, and on `closed` it removes it. Before that workflow the entry was nobody's job, which is why the allowlist reached 103 entries with three branch aliases among them and every open PR's preview was refused. Four things not to undo:

- **It fires on `VERCEL_ENV === "preview"` only.** Production and localhost already land on trusted origins; widening it would put the environments that work behind a variable the function has no reason to second-guess.
- **`page.tsx` is a server component purely to read that variable**, with the form split into `sign-in-form.tsx`. `VERCEL_BRANCH_URL` is not `NEXT_PUBLIC_`, and prefixing it to reach the client would inline an internal hostname into every visitor's bundle to solve what one prop solves.
- **A wildcard trusted domain is not the shortcut it looks like.** Neon wildcards a whole hostname segment, and Vercel varies the hash _inside_ the first label, so the only pattern that matches is `https://*.vercel.app` — every Vercel site on the internet, trusted as a redirect target.
- **The workflow edits `main`'s allowlist, not the PR's own Neon branch.** Every Neon branch has its own auth endpoint, users and allowlist, and Vercel's Preview environment pins `NEON_AUTH_BASE_URL` to main's — so main's list is the one a preview is checked against. Pointing `--branch` at the auto-created `preview/<branch>` would add the domain to an instance no deployment talks to, and the workflow would go green while sign-in kept returning 403.

**The sign-in form checks the returned `error`, not just `catch`.** The Neon client hardcodes `throw: false` into its better-fetch options, so a refusal resolves as `{ data: null, error }` rather than rejecting; the `try`/`catch` alone left the button on "Redirecting…" indefinitely and reported nothing. **Google is the only button because `google` is the only enabled provider** — a `provider` the project has not enabled returns `400 PROVIDER_NOT_SUPPORTED`, which is what the GitHub button did in every environment until it was removed. Adding a button back means enabling the provider in Neon first.

## Query-string state

**The Postings table keeps its view in the URL — sort, direction and page — and that query string is the app's first untrusted GET input.** Everything else the app parses arrives through a form it rendered; a query string arrives however somebody typed it, and there is no submit button to refuse. `lib/postings/posting-query.ts` owns the parse and imports nothing from Next, which is what makes "how does a hand-edited URL degrade" a testable question at all; the page awaits `searchParams` — a `Promise` in Next 16, with a repeated parameter arriving as `string[]` — and hands over the plain object. Four properties, and each is easy to undo:

- **It degrades to defaults; it never errors.** `parsePostingQuery` is total by construction: every field carries its own `.catch()`, so `?page=abc&sort=title` keeps the sort and quietly fixes the page. A whole-object `safeParse` would fail as a unit and throw away a perfectly good sort because a number beside it was nonsense — and **a 500 is the wrong answer to a URL somebody edited by hand.**
- **Nothing in a query string may ever name a user.** The session is the only source of identity: `requirePageUser()` runs _before_ `searchParams` is touched, and the `userId` reaching `listPostings` and `listCoverLetters` comes from it, never from the URL or a form. A parameter that selected rows by owner would be an authorization decision taken from the address bar. Same rule as the Server Actions above, one input earlier.
- **A value that becomes a query is bounded before it gets there.** `page` is capped at `MAX_PAGE` before it can become a `skip`, because an arbitrarily large offset is a scan the database performs for a page that cannot exist; the clamp against the _real_ page count happens in `lib/postings/list-postings.ts`, the only module that knows the total. The sort keys are the URL's own spelling and deliberately not Prisma field names, so what sits in the address bar is not a database column to probe by editing it.
- **The links the app builds omit every default** (`postingsHref`), so the canonical first page is a bare `/jobs` rather than the same page under `?sort=lastSeen&dir=desc&page=1` — a URL nobody would choose to share.

## `DEV_AUTH_BYPASS=1` — the one thing that turns the gate off

**Set it in `apps/dashboard/.env.local` and `next dev` serves every page as a fixed fake user, from fixtures** — no `DATABASE_URL`, no AWS credentials, no `NEON_*`. It exists because editing a component otherwise costs an OAuth round trip, and what renders then depends on whatever is in that Neon branch.

`lib/dev/mode.ts` is the only module that reads the variable, and **it throws when the flag is set under `NODE_ENV=production`** rather than quietly returning `false`. That fires during `next build`, not at the first request — `app/api/auth/[...path]/route.ts` makes page-data collection evaluate `lib/auth/server.ts` at module scope — so such a build cannot be produced at all. Local cost: `pnpm build` fails while the flag is in `.env.local`.

Six accessors branch on `devMockEnabled()`, each before reading any configuration:

- **`lib/auth/current-user.ts`** returns the fixed `DEV_USER`. The one that matters — every page, action and API route asks through it, so **nothing else needs an auth branch**.
- **`lib/db.ts`** and **`lib/storage.ts`** hand out `lib/dev/fake-prisma.ts` and `lib/dev/fake-stores.ts`, memoized through the same variables so a briefing paused on `/jobs/schedules` reads as paused on `/jobs`.
- **`lib/auth/server.ts`** takes placeholder config — the only reason the app boots with `NEON_AUTH_BASE_URL` unset, since the instance is built at module scope. Nothing calls it.
- **`proxy.ts`** returns `NextResponse.next()`. Needed _as well as_ the `getCurrentUser()` branch: `gate` resolves its own session and would redirect every GET first.
- **`lib/briefing-runs/invoke-worker.ts`** hands out `lib/dev/fake-invoker.ts` instead of a `LambdaClient`, so **Run now** works with no role and no function name. The fake deliberately **returns immediately and finishes the run six seconds later**, through the same `finishRun`/`recordRunFindings` the worker uses — an invoker that completed synchronously would make the in-flight UI, which is most of that feature, impossible to see without deploying.

Two things not to "fix": the fake Prisma **throws by name on unimplemented queries** instead of answering `undefined`, and implements `$executeRaw` because `updateJobSchedule()` is raw SQL matched by position (`fake-prisma.test.ts` catches that statement changing). It implements `$queryRaw` for the same reason — `latestRunPerJob()` needs `DISTINCT ON`, which Prisma's model API cannot express. And **`list()` in the fake stores returns less than `head()`**, as the real ones must — supplying the metadata would make the bucket look like a place a display name can be read from cheaply, which is the assumption `/documents` was built on before `documents` in Postgres replaced it.

**A Document is two fixtures and they have to agree.** `devUploads()` is the bytes in the fake bucket and `devDocuments()` is the row in the fake database; a row's `id` is its object's `resumeId`, and `DEV_DOCUMENT_IDS` in `lib/dev/fixtures.ts` is what pairs them. Each half alone reproduces a real production state — an object with no row is invisible, a row with no object lists fine and 404s on download — so neither is a useful default here. `fake-prisma.ts` throws by name on an unimplemented query, so `/documents` under the flag depends on its `document` delegate existing at all.

**Eight things still call OpenAI under the flag; everything else is offline.** `/api/chat`; **Suggest from my resume** on the new-briefing form on `/jobs/schedules` (`lib/jobs/suggest-criteria-actions.ts`, which runs the profile extractor over the user's CV to propose search criteria into the form); **Suggest related titles**, beside it and on each briefing's criteria editor (the same module, which runs the role-title suggester over the same CV plus the titles already chosen — it is the one action in the app that reads a form field _and_ prompts a model with it); **Draft cover letter**; **Generate tailored resume**; the **whiteboard** (`lib/whiteboard/whiteboard-handler.ts`); **Add posting** on `/jobs` (`lib/postings/add-by-link-actions.ts`, which runs the posting extractor over a page a fetcher retrieved); and **scoring postings against the resume** (`lib/postings/match-actions.ts`). Each carries its own seam to fake it — `ChatHandlerDeps.createAssistant`, `SuggestCriteriaActionsDeps.createProfileExtractor`, `SuggestCriteriaActionsDeps.createRoleTitleSuggester`, `CoverLetterActionsDeps.createCoverLetterWriter`, `TailoredResumeActionsDeps.createResumeTailor`, `WhiteboardHandlerDeps.createWhiteboardAgent`, `AddByLinkActionsDeps.createPostingExtractor`, `MatchActionsDeps.createMatchAssessor` — one per composition root rather than one shared, because a single seam would be a further thing to keep in step with `devMockEnabled()`. Each takes the exact name `@workspace/agents` exports for the agent it builds (`NAMING.md` R2, checked by `lib/naming.test.ts`), which is why every one of these modules imports the real factory under a `default…` alias: the seam would otherwise shadow it.

⚠️ **The last one is the only one nobody clicks.** `components/jobs/postings/score-pending-matches.tsx` starts it on mount, so opening `/jobs` spends model calls on every Posting not yet scored against the current resume — and under the flag that means the fixtures. `devMatch()` in `lib/dev/fixtures.ts` therefore scores two rows in every three against `DEV_DOCUMENT_IDS.markdownCv`, which is the _newest_ document labelled Resume: naming the PDF instead would make every row stale and every page view a full re-score of thirty advertisements.

**Add posting is also the only path that reads a key of its own, and which key depends on the link.** A SEEK or Indeed URL goes to that board's Apify actor and needs `APIFY_TOKEN` — no model at all, so no `OPENAI_API_KEY` on that branch. Everything else goes to Tavily and needs `TAVILY_API_KEY` _and_ `OPENAI_API_KEY`. Both are in `turbo.json`'s `globalEnv` and both come down with `neon env pull`, but nothing in the dashboard read either before this feature, so a missing one is invisible until somebody pastes a link — and which one is missing depends on what they paste.

**None of the eight is faked by default, so `OPENAI_API_KEY` is still required to click any of them locally — and to open `/jobs` at all, since the scoring loop needs no click.** The seams exist for the test suites, which pass fakes; nothing under the flag reaches for them. That is deliberate for the two document paths in particular — what you are usually checking under `DEV_AUTH_BYPASS=1` is what the model actually returns for a real advertisement, and a canned reply would make the one interesting part unobservable.

**Only the model call is live in the five that read the CV — the read path is fully mocked.** `loadCandidateBackground()` asks the fake **database** for the newest document labelled `resume` and the fake **store** for its bytes, and the fixtures supply both: `DEV_CV_MARKDOWN` in `lib/dev/fixtures.ts` is the `.md` object, and `devDocuments()` carries the matching `docType: "resume"` row. So nothing else in those actions needs a branch, because each reaches storage through `getResumeStore()`, `getCoverLetterStore()` or `getTailoredResumeStore()` and the database through `getPrisma()`, all of which already have one.

**The app shell lives in `app/(app)/layout.tsx`, and navigation speed is why.** `SidebarProvider`, `AppSidebar` and `SiteHeader` belong to that one layout; `/`, `/jobs`, `/jobs/schedules`, `/jobs/letters`, `/documents`, `/whiteboard` and `/settings` sit under the group and render only a `<main>`. A route group rather than the root layout, because `/auth/sign-in` and `/auth/refused` must render without a sidebar — the parentheses keep the URLs unchanged.

Each page used to render the shell itself. That put it inside the segment being swapped, so every navigation tore the sidebar down, re-rendered it on the server and remounted it; hoisting it buys Next's guarantee that layouts "preserve state, remain interactive, and do not rerender" on navigation. Three consequences, each easy to undo:

- **`app/(app)/loading.tsx` is load-bearing, not decoration.** Every page here is `force-dynamic`, and per `next/dist/docs/01-app/02-guides/prefetching.md` a dynamic page is not prefetched _at all_ without a `loading.js`, and its client cache TTL is off. Deleting it silently restores the original symptom: a click that blocks on a full server render while the previous page stays on screen. Keep it shape-agnostic — one file covers a chat, a document list and a settings panel.
- **`SiteHeader` reads `usePathname` and takes no `title` prop.** It has to: it now sits in a layout that does not re-render, so a title threaded down from the page would be captured once and be wrong for every route after the first. Titles come from `lib/nav.ts`, which is also what the sidebar renders, so the heading and the nav item cannot drift.
- **`staleTimes.dynamic` in `next.config.ts` is safe only because the document actions call `refresh()`.** The default is 0 — no client caching at all — which made every revisit a fresh server render. Raising it lets a segment be reused for 30s; the `refresh()` after an upload or delete is what stops a stale list outliving a change the user just made.
