## Question

How do changes reach Azure? Decide: the CI system (GitHub Actions is the default candidate — the repo lives on GitHub); how CI authenticates to Azure (OIDC federated credentials vs stored service-principal secret); what triggers a deploy (push to main, tag, manual) and whether IaC and worker code deploy in one pipeline or two; and how Turborepo filtering keeps the pipeline from rebuilding the dashboard for a worker-only change.

## Resolution

**CI system: GitHub Actions**, generated by `azd pipeline config` (ticket 07's choice of `azd` cashes in here) against the `azure.yaml` service definition — this scaffolds the workflow file rather than hand-writing one from scratch, reducing the chance the implementation effort invents a divergent shape.

**Authentication: OIDC federated credentials, not a stored secret.** `azd pipeline config` sets this up by default: it creates an Azure AD app registration with a federated identity credential scoped to this repo + branch, and the workflow authenticates via `azure/login` with `client-id`/`tenant-id`/`subscription-id` repo secrets (non-sensitive identifiers, not a rotatable credential) plus GitHub's own OIDC token — no long-lived service-principal secret is stored anywhere. This fits the "no secret value ever lands in this tracker" line already established for `OPENAI_API_KEY` (ticket 07): the same discipline extends to the deploy credential itself.

**Trigger: push to `main`, plus manual dispatch.** No tag-based release process exists in this repo and none is needed for a single personal-subscription worker — every merge to `main` that touches the worker or its infra should reach Azure directly (this is a greenfield personal project, not a multi-stage release pipeline; ticket 07 already ruled out a dev/prod split for the same reason). `workflow_dispatch` is added alongside the push trigger so a run can be forced without an empty commit — e.g. after the one-time manual Key Vault secret step (ticket 07), to confirm the app picks it up.

**One pipeline, not two: infra and worker code deploy together, via `azd deploy` semantics (`azd provision` + `azd deploy` combined, i.e. `azd up` in CI).** Splitting Bicep and app-code deploys into separate workflows would require them to be kept in sync by hand across two files for one small service; a single workflow that provisions (idempotent — no-ops when infra is unchanged) then deploys the worker's zip keeps the "one decision, one place" property the rest of this map has favored (e.g. ticket 05 folding the observability decision into the compute-service ticket rather than splitting it out).

**Turborepo filtering — path-scoped triggers, not a Turbo command.** The workflow's `on.push.paths` is scoped to `apps/briefing-worker/**`, `packages/agents-core/**`, `packages/agents/**`, `packages/agent-tools/**`, and `infra/**`/`azure.yaml` (`workflow_dispatch` has no `paths` filter — a manual run always runs) — so a dashboard-only or UI-package-only push never triggers this workflow at all, which is stronger than relying on `turbo build --filter` to no-op, and cheaper (no checkout/install cost for an irrelevant change). Inside the workflow, the actual build step still runs through Turborepo — `pnpm turbo build --filter=@workspace/briefing-worker` — so `build.dependsOn: ["^build"]` (ticket 06) correctly builds `@workspace/agents-core` and `@workspace/agent-tools` first, exactly as it would locally; Turbo's remote-cache benefit is secondary here (one small app, infrequent pushes) and not itself relied on for correctness.
