## Question

How is the Azure side expressed and organized? Decide: the IaC tool (Bicep, Terraform, or azd) and where its files live in the repo; resource-group layout and a naming convention for the greenfield subscription; whether one environment suffices for now or dev/prod split from the start (graduates the multi-environment fog item); and the secrets/config strategy — where `OPENAI_API_KEY` lives (Key Vault vs service-native secrets), how the worker reads it, and how the cadence value is configured and changed. Record the conventions precisely enough that the implementation effort never invents a name.

## Resolution

**IaC tool: `azd` (Azure Developer CLI), Bicep underneath.** Ticket 05 already flagged that an official azd TypeScript Functions-timer starter has the strongest template coverage of the shortlisted options — picking azd here cashes that in, and it also gives ticket 08 (CI/CD) a built-in `azd pipeline config` command that scaffolds the GitHub Actions workflow and OIDC federation, cutting a decision there down to "accept the default." Terraform is not used anywhere in this repo and would add a second state-management story for one small service; plain hand-rolled Bicep with no azd wrapper would forgo the starter template and the pipeline scaffolding for no benefit. Files live at the repo root — `azure.yaml` (azd's manifest, `services.worker.project: ./apps/briefing-worker`, `language: ts`, `host: function`) and `infra/*.bicep` (generated by `azd init` from the Functions-timer starter, then edited for this repo's specifics below). Root-level, not nested under the app, because azd's own convention expects `azure.yaml` at the project root and this repo may host more than one deployable service later.

**Resource-group layout and naming: single group, azd's own convention, not a hand-rolled one.** One resource group for everything this map produces — greenfield personal subscription, one worker, no reason to split. Naming follows whatever the chosen azd starter's `main.bicep` already defines (Azure CAF abbreviations + a `resourceToken` derived from `uniqueString(subscription().id, environmentName, location)`) rather than this ticket inventing a parallel scheme that would just fight the template — the one value this ticket pins, so the implementation effort never has to invent _it_, is the **azd environment name: `briefing`**, which seeds that token deterministically. Expected shape from the standard starter, to confirm at `azd init` time: resource group `rg-briefing`, function app `func-briefing-<token>`, the Functions-required storage account `st<token>` (see persistence note below), App Insights `appi-briefing-<token>`, Log Analytics `log-briefing-<token>`, Key Vault `kv-briefing-<token>` (Key Vault names are capped at 24 characters — the starter's Bicep truncates the token for this resource specifically; do not hand-write a longer name), and the system-assigned managed identity ticket 05 already decided lives directly on the function app rather than as a separate identity resource.

**Environments: single environment, no dev/prod split.** This graduates the "multi-environment story" fog item — resolved as: not needed. One human, one greenfield personal subscription, one daily proof run; a dev/prod split would double every resource for no consumer of the "dev" side. Azd environment name is `briefing` (see above), region `australiaeast` per ticket 04. Revisit only if a second consumer (e.g. a staging slot before the real Briefing ships) materializes.

**Persistence note (not a contradiction of ticket 03):** ticket 03 ruled out an _application-level_ persistence primitive for the proof — that stands. But Azure Functions itself mandates a storage account for its own host/deployment-package state on every plan including Flex Consumption; that storage account is a **platform requirement**, provisioned by the azd starter's Bicep automatically, and the worker's own code never reads or writes to it. Nothing here reopens ticket 03.

**Secrets: Key Vault + system-assigned managed identity, per ticket 05.** `OPENAI_API_KEY` is stored as a Key Vault secret named `openai-api-key`; the function app setting is named `OPENAI_API_KEY` — verified against `packages/agents-core/src/env.ts`'s `getOpenAIApiKey()`, which reads `process.env.OPENAI_API_KEY` directly, no other name — set to a `@Microsoft.KeyVault(SecretUri=...)` reference, resolved at runtime via the function app's system-assigned identity holding the **Key Vault Secrets User** role on that vault (RBAC authorization model, not the legacy access-policy model — Bicep should set `enableRbacAuthorization: true`). The Bicep provisions the empty Key Vault and the RBAC role assignment only; it never contains the secret's value. **Getting the value in is a one-time manual step**, not part of any pipeline: `az keyvault secret set --vault-name kv-briefing-<token> --name openai-api-key --value <key>`, run once by hand after `azd provision`, documented in the handoff spec (ticket 09) as a manual post-provision step — consistent with "no secret value ever lands in this tracker" (ticket 05).

**Cadence configuration: in code, per ticket 05's existing decision — this ticket only supplies the concrete value.** Ticket 05 already removed the "how cadence is configured" fog item on the basis that the NCRONTAB string lives directly in the `app.timer()` trigger binding in `scheduledRun.ts` (ticket 06), not as an app setting — changing the schedule means editing that string and redeploying, not an `azd env set`. No app-setting indirection is introduced here, since none was decided. Concrete value: **`0 0 9 * * *`** (09:00 UTC daily) — an arbitrary but concrete choice so the implementation effort doesn't have to invent one; trivially changed later since it's one line in one file.
